目标：一次性完成在线图标管理、统一目录、自动审核、人工审核、Gitee 发布、Launcher 自动匹配、跨应用跳转、自定义图标共享、原版锤子桌面对接及自动更新。

# 一、最终产品架构

## 1.1 三个核心部分

### A. Smartisan Icon

定位：独立在线图标管理工具。

主要功能：

- 展示手机已安装应用。
- 自动识别已适配、未适配、待审核状态。
- 浏览全部在线图标。
- 搜索、分类、详情、候选变体。
- 用户发起适配请求。
- 用户上传自定义图标。
- 查看投稿和审核进度。
- 管理员审核、下架、恢复图标。
- 在线目录、版本、缓存及网络诊断。

不再将 5199 枚完整 PNG 作为 APK 内置资源。

首页显示手机已安装应用，全部图标放在第二个 Tab。

### B. Smartisan Launcher

定位：图标实际使用客户端。

以现有坚果 Pro 3 原版提取及移植工程为开发基线。

主要功能：

- 自动匹配在线图标。
- 显示适配状态。
- 手动选择图标及候选变体。
- 未适配应用直接跳转 Smartisan Icon。
- 自定义图标共享到 Smartisan Icon。
- 自动刷新在线目录。
- 自动更新图标缓存。
- 下架图标同步失效。
- 保留原有桌面布局、动画、文件夹、负一屏和备份功能。

禁止重新实现已有的图标加载、数据库和缓存机制。

### C. NAS + Gitee

NAS 是业务管理和审核中心。

Gitee 是正式公开图标资源分发仓库。

职责：

NAS：
- FastAPI 服务。
- SQLite 数据库。
- 用户、管理员、权限。
- 投稿、审核、求图、投票。
- 图标技术检测。
- 发布任务队列。
- Gitee API 调用。
- 备份、恢复。
- 公开目录备用服务。

Gitee：
- 官方 PNG。
- 社区 PNG。
- catalog.json。
- index.json。
- variants.json。
- search-index.json。
- release.json。

Gitee Token 只允许保存在 NAS 服务端环境变量中，绝不进入 Android APK。

不新增独立云服务器作为前提。

# 二、统一数据源：最高优先级原则

## 2.1 单一公开事实来源

两个软件不能分别计算适配状态。

统一规则：

**当前正式发布的 Catalog Snapshot 是所有客户端判断适配状态的唯一依据。**

NAS 数据库负责管理投稿和审核状态。

Gitee 正式发布快照负责定义哪些图标真正公开可用。

客户端不得通过本地投稿记录、历史搜索结果或自行维护的包名表判定全局适配状态。

## 2.2 统一资源身份

必须保持现有 Launcher 合同：

- 官方 sourceId 保持原值。
- 社区 sourceId 使用 ch-<ULID>。
- PNG 文件保持 icons/drawable/<sourceId>.png。
- catalog packages/components 语义不变。
- variants 候选顺序保持有效。
- Launcher 持久化格式 resource:<sourceId> 不变。

内部数据库 ID、API 路由 ID、公开 sourceId 必须分开管理。

不得把 official:<sourceId> 当作公开资源 ID。

## 2.3 适配状态定义

| 状态 | 是否算已适配 |
|---|---|
| 正式发布且未下架 | 是 |
| 待审核 | 否 |
| 审核通过、尚未正式发布 | 否 |
| 发布处理中 | 否 |
| 被退回 | 否 |
| 已下架 | 否 |
| 仅本机自定义图标 | 否，单独显示本机自定义 |
| 网络暂时不可用 | 沿用上次有效快照，不得误判为未适配 |

适配判断顺序：

1. 精确组件映射。
2. 明确包名映射。
3. variants 候选。
4. 没有有效匹配时判定未适配。

禁止模糊搜索结果直接参与自动匹配。

## 2.4 统一 revision

每次正式发布、更新、下架、恢复，都产生新的 releaseId / revision。

Smartisan Icon 和 Launcher 必须记录：

- 当前 revision。
- 上次同步时间。
- 当前快照来源。
- 快照完整性。
- 是否需要更新。
- 当前离线状态。

两个软件不能各自拥有一套独立的适配状态缓存。

# 三、Gitee 与 NAS 发布架构

## 3.1 镜像顺序

正式运行策略：

1. Gitee 优先。
2. NAS HTTPS 静态元数据及资源备用。
3. GitHub 不作为正常运行依赖，保留为可选紧急恢复渠道。
4. 全部网络不可用时使用最后一次有效本地快照。

特别处理 Gitee 451：

451、403、5xx、DNS、TLS、超时均属于镜像失败，不能认为图标不存在。

只有所有可用来源都明确返回 404，才可以判定资源不存在。

目前 Gitee 的 index.json 和 variants.json 返回 451，必须在 S2 阶段解决：

- 先核实 Gitee 内容审核原因。
- 通过 Gitee 正常申诉或修正被拦截内容。
- 恢复前由 NAS 提供同一 revision 的备用元数据。
- 不允许用不完整目录替代正式目录。

不得以绕过平台内容审核的方式处理 451。

## 3.2 统一发布清单

新增 release.json，至少包含：

- schema。
- releaseId。
- revision。
- createdAt。
- catalog 文件地址。
- 四份元数据 SHA-256。
- 官方图标数量。
- 社区图标数量。
- 总图标数量。
- 被下架资源清单或 tombstone。
- 最低客户端协议版本。

客户端先读取 release.json，再按其中记录获取对应快照。

## 3.3 发布顺序

必须使用可恢复的发布任务：

1. 读取已经审核通过的投稿。
2. 校验 PNG 和元数据。
3. 上传社区 PNG 到 Gitee。
4. 公开访问并验证 SHA-256。
5. 读取官方快照。
6. 合并官方及社区目录。
7. 生成 catalog.json。
8. 生成 index.json。
9. 生成 variants.json。
10. 生成 search-index.json。
11. 运行统一目录审计。
12. 上传完整版本化元数据。
13. 校验四份文件的 SHA-256。
14. 最后发布 release.json 指针。
15. 再次公开读取 release.json 验证。
16. 全部成功后才将作品置为 published。

元数据建议使用版本化发布目录，避免多文件更新过程中客户端读到混合版本。

旧 release 保留，支持回滚。

任何步骤失败：
- 不得置为 published。
- 保留 approved 状态。
- 任务进入可重试状态。
- 管理员能够查看失败步骤。
- 不影响当前正式 release。

## 3.4 官方目录

使用已经审计通过的 Launcher 镜像快照作为官方基线。

不要重新制作第二套官方 PNG。

服务端保存四份官方元数据及 SHA-256 清单。

社区数据与官方数据合并时，严格复用 Launcher 的 icon_library.py 生成和审计规则。

不得重命名官方 sourceId。

# 四、自动审核 + 人工审核

## 4.1 自动审核

所有上传首先进入技术审核。

检查项目：

- PNG 文件魔数。
- PNG chunk CRC。
- IHDR、IDAT、IEND。
- 图片尺寸。
- 文件大小。
- 透明通道。
- 解码合法性。
- SHA-256。
- 完全重复图片。
- 感知哈希相似图。
- 包名格式。
- Activity 合法性。
- 元数据完整性。
- 授权及来源声明。

自动审核通过不代表正式发布。

## 4.2 人工审核

管理员检查：

- 是否为正确应用。
- 是否符合 Smartisan 图标风格。
- 是否存在明显抄袭或侵权风险。
- 是否与现有候选重复。
- 是否需要归入某个已有应用的 variants。
- 名称、分类、包名和组件是否正确。
- 是否符合公开发布要求。

审核通过后进入发布队列。

退回后允许作者修改并重新提交。

## 4.3 管理员权限

超级管理员：
- 所有管理权限。
- 创建和管理普通管理员。
- 配置管理员权限。
- 下架、恢复、发布和回滚。

普通管理员：
- 按授权范围审核投稿。
- 管理图库。
- 查看和处理求图请求。
- 不得修改超级管理员权限。

所有审核、发布、下架操作记录审计日志。

# 六、Launcher 对接

## 6.1 保留原有核心代码

优先复用：

- IconLibraryCatalog。
- IconPreviewRepository。
- IconPackManager。
- RedirectIconDB。
- IconManager。
- IconLibrarySearchPage。

不得重建第二套图标下载器。

## 6.2 动态目录更新

当前 Launcher 全库搜索读取 APK 内置 search-index.json。

增加统一在线目录同步能力：

1. 后台检查 release.json。
2. revision 不变直接复用。
3. revision 改变下载新快照。
4. 校验四份元数据。
5. 后台解析。
6. 原子切换目录快照。
7. 更新内存匹配索引。
8. 只使受影响的应用和图标缓存失效。
9. 通知桌面刷新图标。

保留旧 APK 内置目录作为首次启动及更新失败的兜底。

不得因为一次网络故障清空有效目录。

## 6.3 图片缓存

沿用现有在线图标缓存体系。

新增 per-sourceId 的 SHA-256 / revision 感知。

同名 sourceId 图片内容变化时：

- 校验新 SHA。
- 原子替换缓存。
- 只清理对应图标的内存缓存。
- 通知对应桌面应用刷新。

不要每次更新都清空整个 64 MiB 图标缓存。

## 6.4 自动刷新

- 桌面冷启动：读取本地快照。
- 后台空闲：检查 revision。
- 网络恢复：触发一次检查。
- 收到正式更新：更新受影响的图标。
- 下架：停止自动匹配该资源。

图标刷新不能阻塞 HOME 首帧。

# 七、两个软件之间的 Intent 协议

升级现有 protocol/iconhub-intent-v1.md。

## 7.1 Launcher → Smartisan Icon

增加：

ACTION_REQUEST_ADAPTATION：

传递：
- protocol。
- package。
- activity。
- app label。

打开对应应用的适配详情，并允许用户一键发起求图。

ACTION_PREPARE_UPLOAD：

传递：
- package。
- activity。
- app label。
- 可选 icon content URI。

自动填充投稿信息。

ACTION_PICK_ICON：

传递目标应用包名和组件。

IconHub 返回：
resource:<sourceId>

Launcher 直接调用已有 RedirectIconDB.updateResourceIcon() 保存。

## 7.2 自定义图标共享

Launcher 现有 custom 图标数据必须能够导出。

采用只读 ContentProvider 或 FileProvider URI：

- 不传 file://。
- 不开放整个 filesDir。
- 仅授予当前 URI 读取权限。
- IconHub 将文件复制到自己的私有投稿草稿目录。
- 用户明确确认共享后才上传。
- 不自动上传用户全部自定义图标。

## 7.3 Intent 安全

- 校验协议版本。
- 校验包名。
- 校验 MIME。
- 校验文件尺寸。
- 处理对端未安装。
- 处理取消。
- 处理重复 Intent。
- 处理 Activity 重建。

不能把跨应用 Intent 当作公开可信数据。

# 八、锤子原版桌面对接

以当前坚果 Pro 3 提取版为统一核心代码基线。

锤子手机不要求用户安装第二个独立桌面。

需要提供两种构建及集成路径：

A. 其他 Android 手机：
正常安装我们的 Launcher APK。

B. Smartisan OS：
将增加在线图标功能的 Launcher 集成到原版系统桌面。

必须检查：

- 原版 Launcher 包名。
- 原版签名。
- 当前 ROM 版本。
- 原 APK 版本。
- 系统权限。
- Android API。
- System 分区及启动恢复方式。

如果 OEM 系统签名不一致，不能普通覆盖安装。

需要使用经过验证的系统级替换、ROM 补丁或恢复方案。

先以坚果 Pro 3 原版 ROM 为基准完成验证，再按 ROM 版本建立兼容配置。

不允许为不同手机建立独立图标库。

不得直接覆盖用户唯一的系统桌面 APK。

必须提供原版 APK 备份和失败恢复方案。

# 十二、最终验收标准

必须同时满足：

1. Smartisan Icon 首页显示本机应用，不再显示完整离线图库。
2. 全部图标来自统一在线 Catalog。
3. 两个软件的适配状态完全一致。
4. Launcher 未适配应用可以跳转 IconHub。
5. IconHub 未适配应用可以直接发起求图。
6. 用户可以共享 Launcher 自定义图标。
7. 自动审核与人工审核完整运行。
8. 审核通过后 Gitee 自动发布。
9. 两个软件自动获取新 revision。
10. 桌面图标自动刷新。
11. 管理员下架后两个软件同步失效。
12. 断网使用上次有效快照。
13. Gitee 失败时 NAS 能够备用。
14. 不依赖 GitHub 才能完成正常业务。
15. 不破坏原版桌面的核心功能。
16. 不打包完整 PNG 图库。
17. 真机完成整个投稿到桌面更新的闭环。
18. 所有测试、构建、日志和恢复证据归档。

**最终产品原则：一套图标库、一套适配规则、一个发布版本、两个客户端。任何一个客户端都不允许自行维护另一份适配真相。**
